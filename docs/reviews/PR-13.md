## 4. The two "ladder bugs"

Both filed in `docs/BUGS.md` (2026-08-30 rows), each pinned by a
failing-before/passing-after test in `tests/gate/passes/adversarial-ladder.test.ts`.

**1. `global-access` folds position-blind — REAL.** `isProvenGlobal`
(`match.ts`) is whole-function and position-blind; a register clobbered later
in a repeating loop body still "proves" global from iteration 2 on. I ran the
test's own `vm.runInContext` repro by hand: un-rewritten program correctly
prints `GLOBAL, OTHER`, the rewritten one wrongly prints `GLOBAL, GLOBAL`.
This is legitimately Node-verifiable with **no D14 risk** — plain property
reads/writes under a global write, no per-iteration `let`, no TDZ, no
`arguments` aliasing, nothing Hermes and any other ES engine would disagree
on. Real bug, correctly classified, correctly left for the M5 pass-ladder lane
(off-limits to this PR).

**2. `maxDepth` guard doesn't protect a cold process — REAL, but the exact
numeric boundary is machine/Node-version-fragile.** Confirmed: on my machine
(macOS arm64, Node 25.9.0 — inside the project's own `engines: ">=22.18.0"`,
no upper bound), the probe's "1000 blocks should structure cleanly"
*positive control* itself throws `RangeError` (reproduced deterministically,
twice). This isn't D14-related and needs no VM — it's a raw V8 stack fact —
but it shows the harvested boundary (~1030 OK / ~1075 crash) is specific to
the machine/Node build it was measured on and doesn't generalize. On the
actual CI matrix this doesn't currently bite: all four `build-test` jobs
(ubuntu/macos × Node 22.18/24) ran the full gate, and the only failure across
all of them was the pre-existing, already-disclosed `2000 deterministic
mutants ... always terminate quickly` timing flake (macOS 22.18 only) — not
the maxDepth test. Recommend the M5 lane fix note this fragility (measure
per-invocation or use a much larger safety margin) rather than trust the pinned
numbers across environments, but it does not block this PR.
