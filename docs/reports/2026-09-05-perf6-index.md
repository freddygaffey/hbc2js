# 2026-09-05 -- perf part 6: a per-register position index for the classify scan

Ledger row: `docs/BUGS.md` 2026-09-01 "passes-superlinear-term-2" (the
"452 s / 946 s" row). Evidence this session starts from:
`docs/reports/2026-09-05-nsw-retime.md` and its Mac re-time at 3775286
(whole-file `--lenient-env`, 519.5 s wall / 546 s CPU), whose top self-time
frames are `nextRelevant` (75.7 s + 53.4 s at two call sites) and
`stmtInterest` (59.1 + 45.8 + 41.1 s) -- ~275 s of 546 s -- plus
`identUsesMany` 41 s and `classifySite` 23 s.

Everything below is measured on this Mac. Micro-benchmarks are CPU ms
(`process.cpuUsage`); the bundle runs are `/usr/bin/time -l`.

## What the scan actually costs (measured before any change)

Generator: the one `tests/gate/passes/expr-rebuild-perf.test.ts` already
uses, extended with the module-root shape the NSW profile points at -- a
register stored once and *never mentioned again*, so `nextRelevant`'s answer
is "there is none" and the scan runs to the end of the list.

| shape | before | after |
|---|---|---|
| S1: 500 `classifySite` calls, dead stores + inert tail of 0 | 7.4 ms | 3.7 ms |
| S1, tail 2,000 | 23.4 ms | 6.2 ms |
| S1, tail 8,000 | 92.2 ms | 31.6 ms |
| S1, tail 20,000 | 219.9 ms | 39.5 ms |
| S2: driver, 4,000 store+read sites, unique register each | 1045 ms | 1315 ms |
| S3: driver, 4,000 dead-store sites, unique register each | 1555 ms | 1182 ms |

S1 is the isolated claim: 500 sites cost 30x more with a 20,000-statement
inert tail behind them than with none, for work none of them needs to look
at. After the change the same measurement is 10.7x (and most of what is left
is the index build, `O(list.length)` *once* per list identity rather than
once per site).

S2 is the counter-measurement: a shape where the scan was already short
(every register is read by the very next statement) pays for the index
without using it -- 26% worse. It is also deliberately adversarial for the
derivation, giving every one of its 4,000 sites a register name of its own,
so `noteStmtIndexSplice` iterates 4,000 single-entry position lists per
splice. A real register frame does not grow that way (see
`docs/reports/2026-09-05-perf5-match-scan.md`, which makes the same note
about `noteRegisterUsesSplice`'s map copy).

## The design, and the two that were rejected

**Shipped**: `src/passes/expr-rebuild/stmt-index.ts` -- one sorted position
list per register name, plus one each for "contains a jump" and "is a
fall-through compound statement", built lazily per list identity (only for
lists of 128 statements or more; below that the scan is cheaper than the
build) and then *derived* across each applied splice by
`noteStmtIndexSplice`, called from `check.ts` beside the existing
`noteRegisterUsesSplice`. The derivation is sound on exactly the premise
that call already relies on: `verifyExpectedShape` has proven, position by
position, that `after` is `before` with the window `[i, hiBefore)` replaced
by `[i, hiAfter)`, so entries below `i` are unchanged, entries at or after
`hiBefore` shift by the constant length delta, and only the inserted window
needs a `stmtInterest` lookup. `passThroughCount` became
`anyPassThroughBetween` in the same change: its one caller only ever asked
whether there is a pass-through statement in the gap, never how many, and
"is there one" is a single binary search where "how many" would need a
prefix-sum array to maintain.

**Rejected -- rebuild the index per list identity** (this is what part 1
removed, as `listIndex`, when it was the single hottest frame at 59 s). A
rebuild is `O(list.length)` `stmtInterest` lookups *plus* one array
allocation per distinct register, once per applied site: on `fn#0` that is
4,510 rebuilds of a ~9,000-entry structure. Deriving costs one integer add
per surviving entry and allocates nothing.

**Rejected -- stable ids plus a Fenwick tree** (positions never shift; a
bit-indexed tree over "still present" ids converts stable id to current
index in `O(log n)`). This is the only design here that removes the
`Theta(sites x list.length)` term outright, and it fits this pass unusually
well because every `expr-rebuild` splice deletes exactly one statement and
re-tags at most one other, never inserts. It was rejected on cost/benefit,
not on soundness: the writer still materialises one `readonly Stmt[]` per
applied site (docs/PUSHBACK.md P-33/P-34, accepted), which is the same order
of work as the shift this design would remove, so the asymptotic class of a
whole run does not change -- only the constant, and the shift's constant is
already an integer add against the writer's pointer copy. It needs ~150
lines of order-maintenance code and its own soundness proof, and it belongs
with the persistent-list change P-33 names, not before it.

**Rejected -- a patch-returning driver contract** (`applyAstPasses` hands
each pass a patch instead of a whole list). That is the right long-term
answer and would let every pass keep incremental state trivially, but it
changes the `Pass` interface for all fourteen passes and their checkers; it
does not fit this task's ~600-line cap, and doing it under one pass's
deadline would be the worst way to land it.

## Semantics

Unchanged, and checked three ways:

1. `tests/gate/passes/stmt-index.test.ts` -- a differential against the scan
   the index replaced, over random lists at 40 / 130 / 400 statements (both
   sides of the 128 threshold), every `(reg, from)` pair, and then along a
   60-step chain of splices in all three shapes the rewriter produces
   (delete one statement; replace one in place; delete one and rewrite a
   later one). Errors compound along the chain, so a single wrong shift is
   caught.
2. The real bundle: whole-file `--lenient-env` output before and after is
   **byte-identical**, sha256
   `2b087de24ad30e4a0d4533cdbbfac6d7b6b31c9e3ffbfc3e3a193153bace7ee7`
   (60,857,443 bytes).
3. The gate, including `pipeline-speed.test.ts`'s rn-template output hash
   and the T2 equivalence tier.

## The real bundle

`node src/cli.ts decompile nsw.hbc --lenient-env <out>` on the Service NSW
bundle (43,384 functions), this Mac:

| | wall | user CPU | sys | max RSS |
|---|---|---|---|---|
| before (this worktree at f733dc6) | 534.7 s | 498.8 s | 10.0 s | 5.89 GB |
| after | 768.2 s | 471.7 s | 13.8 s | 5.50 GB |

The wall times are **not** comparable: the "before" run had this Mac's 1-min
load average between 3 and 11, the "after" run ran into an unrelated job
that took the load to 34 (768 s wall against 471 s of CPU -- it spent nearly
300 s starved). User CPU is the honest comparison, and it is
**498.8 s -> 471.7 s, a 5.4% improvement**.

That is far less than the ~275 s the pre-change profile attributed to
`nextRelevant`/`stmtInterest`, and the profile below says where it went.

The layer this session was aimed at is gone: `nextRelevant` has no frame at
all (it inlines into `lowerBound`, 6.3 s), and `stmtInterest` is 5.1 s where
the two together were ~275 s of a comparable profile before. What replaced
them in the top of the list is not new work this change added -- the index's
own two frames total 11.4 s -- it is what was always underneath.

So the row's remaining cost is now, in order: `identUsesMany`/`countUses`
(46 s + ~68 s of `visitExpr` across its call sites: D-b's whole-function
register counts, still recomputed per function-generation), GC (47 s, the
allocation the immutable `readonly Stmt[]` architecture forces -- P-33/P-34
again), `emit/function.ts`'s `envParentMap` (24 s, not a pass at all),
`hoistRegisterInits` (12.7 s) and `reg-split`'s `reachesSeq` (10.5 s).

## Verdict

Not met. This change removes the term the row named, and the microbenchmark
that isolates it improves 5.6x, but whole-file NSW moved 498.8 s -> 471.7 s
of user CPU (5.4%), nowhere near the 60-120 s bar. The row stays open, and
its next actionable term is `identUsesMany`'s whole-function count walk plus
the GC pressure of the list representation itself -- i.e. P-33's persistent
list, or memoising the whole-function counts across a *function*'s
generations the way `noteRegisterUsesSplice` already does for one list's.

The gap between "275 s of the previous profile" and "27 s of real CPU
saved" is worth stating plainly rather than explaining away: a `--cpu-prof`
run of this bundle takes 691 s sampled against ~470 s unprofiled, and
sampling inflates small hot leaf functions like `nextRelevant` the most, so
a frame's share of a profiled run is an upper bound on its share of an
unprofiled one. Any future estimate off this row's profiles should be
discounted accordingly.
