# 2026-09-08 -- perf part 7: register counts memoised per statement, not per list

Ledger row: `docs/BUGS.md` 2026-09-01 "passes-superlinear-term-2" (the
"452 s / 946 s" row). This session starts from part 6
(`docs/reports/2026-09-05-perf6-index.md`), whose verdict named the next
term: `identUsesMany`/`countUses`, "D-b's whole-function register counts,
still recomputed per function-generation" -- 46 s of self time plus ~68 s of
`visitExpr` across seven call sites in a 691 s sampled whole-file profile.

Everything below is measured on this Mac (same box as parts 5 and 6).

## What was actually being recomputed

Part 5 already memoised the whole-function register counts on the *list's*
identity (`registerUsesMemo`, a `WeakMap<readonly Stmt[], ...>`) and carried
them across `expr-rebuild`'s own splices (`noteRegisterUsesSplice`). Two
holes were left, and they are where the profile's time was:

1. **Every other pass's rewrite.** Only `expr-rebuild` derives its counts
   across a splice. Every applied site of `var-naming`, `fn-naming`,
   `reg-split`, `spread-rest`, `hoistRegisterInits`, ... hands the next
   caller a fresh `readonly Stmt[]` identity, so the next
   `registerUses(fnBody)` is a cold walk of the whole function -- the
   `Theta(sites x list.length)` term again, one level up from the one part 5
   removed.
2. **`identUsesMany` never used the memo at all.** `identUses(fnBody, rN)`
   (a dozen guards across the passes) and `identUsesMany(before, froms)`
   (`var-naming`'s per-site checker, twice per applied site) each walked the
   whole list themselves, even when the very same counts were sitting in
   `registerUsesMemo`. That is the 46 s frame: it is `identUsesMany`'s own
   `(n) => wanted.has(n)` closure, called once per identifier node visited.

## The change (src/passes/ast.ts, ~90 lines)

**A per-statement memo.** `stmtRegisterUses(s)` is `registerUses([s])`
memoised on the **statement's** identity, exactly the discipline
`expr-rebuild/stmt-index.ts`'s `stmtInterest` already uses. A rewrite reuses
the statement objects it did not touch, so a statement's counts survive
every generation of every list it is ever in.

**`registerUses` becomes a fold.** A cold whole-list walk is now the
componentwise sum of its statements' memoised counts: `O(statements +
names)` map work instead of a full tree walk. Sound because `countUses` is a
left-to-right accumulation with no cross-statement state -- the same
concatenativity `noteRegisterUsesSplice` already relies on, applied one
statement at a time. It reproduces a cold walk key for key *and* in the same
key order (a name's entry is created by the first statement that mentions
it, in list order).

**`identUsesMany` projects when it can.** When every wanted name is a
register name, the query is a restriction of `registerUses`: `countUses`'s
traversal does not depend on `wanted` (the predicate only gates `bump`) and
both use `followNested = false`, so counting "these registers" and "every
register" visit the same nodes and agree name for name. The projection
preserves the previous key order (first-appearance order for names that
occur, then the zero-fill in `wanted` order).

`expr-rebuild/stmt-index.ts`'s `stmtInterest` now calls `stmtRegisterUses(s)`
instead of `registerUses([s])` -- same answer, no temporary one-element
array, and the memo is shared with everything else.

Not changed: `identUsesMany` with any non-register name (`fn-naming`'s
`_fnN`s, `var-naming`'s `to` names) still takes the original `countUses`
path, because `followNested` makes it a different traversal.

## The real bundle

`node src/cli.ts decompile nsw.hbc --lenient-env <out>` on the Service NSW
bundle (43,384 functions), this Mac:

| run | wall | user CPU | sys | max RSS |
|---|---|---|---|---|
| **before** (185a7105), quiet box | **403.0 s** | **426.5 s** | 22.2 s | 4.21 GB |
| **after**, quiet box | **366.9 s** | **317.6 s** | 10.1 s | 4.72 GB |
| before, first pair (load 2-3 at the start, rising) | 681.1 s | 726.5 s | 19.1 s | 4.55 GB |
| after, first pair (load 84: 12% of a core) | 3020.4 s | 504.3 s | 25.9 s | 4.71 GB |

Only the first two rows are comparable, and they are the ones quoted: the
second pair was measured while another agent's job took this Mac's 1-min
load average to 84, which inflates *both* wall and user CPU (cache and
memory-bandwidth contention, plus swap: the box was at 13.3 GB of 14.3 GB).
Part 6 made the same caveat about its own pair; the lesson this session adds
is that user CPU is not immune to it either -- the same before-commit
measured 726.5 s under contention and 426.5 s quiet, a 1.7x spread on a
number the row is graded on. Both pairs agree on the direction and roughly
on the size of the change; neither's absolute seconds should be compared
across sessions without checking the load the run was taken under.

User CPU **426.5 s -> 317.6 s, a 25.5% improvement**; wall 403.0 s ->
366.9 s. The cost is memory: peak RSS **4.21 GB -> 4.72 GB (+12%)**, which
is the per-statement memo (one small `Map` per statement, alive as long as
the statement is). That is the trade this design makes and it is worth
re-checking on any bundle bigger than this one.

## Verdict

Not met. The row's bar is a whole-file NSW `--lenient-env` decompile in
60-120 s; this change takes it from 426.5 s to 317.6 s of user CPU (25.5%)
on a quiet box. The row stays open.

Its next actionable terms, in the order the numbers support:

1. **The per-site checkers' non-register walks.** `var-naming/check.ts` and
   `fn-naming/check.ts` each walk the whole list twice per *applied site*
   (`identUsesMany(before, froms)` and `identUsesMany(after, [...froms,
   ...tos])`), and the second one cannot use the register memo because a
   `to` is not a register name. The same concatenativity argument that
   powers `noteRegisterUsesSplice` applies to them -- these checkers know
   their own splice window -- so this is the direct sequel to this session.
2. **The list representation itself** (GC, 47 s in part 6's profile): P-33's
   persistent list or the patch-returning driver contract. Every term above
   is bounded below by it.
3. `emit/function.ts`'s `envParentMap` (24 s), which is not a pass and has
   never been looked at under this row.

Also worth recording: the memo trades ~0.5 GB of peak RSS for those 109 s.
If a later bundle makes that trade unattractive, the per-statement map can
be dropped for statements whose own count map is empty (the common case for
`break`/`return`/`directive`) without touching the fold's soundness.
