# Lane pack: readability (spec 28, the LLM naming / rewrite / file-op layer)

This file is a lane worker's whole orientation. Read it first, then only the files a task names. It is OWNED BY THE WORKER: the last act of every task is to rewrite it (advance the queue, add gotchas, delete stale lines). The ledgers stay where they are: `docs/BUGS.md` (open bugs, owners), `docs/PUSHBACK.md` (design deviations), `docs/AGENT-LOG.md` (what each task did). Never duplicate them here; point at them.

## What this lane is
An LLM proposes names, function rewrites and file-tree ops for decompiled Hermes bytecode. Every proposal is `suggested` until a human (UI) or an opt-in evaluator promotes it; every accepted change passes the equivalence oracle or is discarded; every change is a reversible, provenance-stamped record. Spec: `docs/specs/28-llm-readability.md` (sections 0a, 1b, 1d, 7, 9.x are the contracts; 10 is the landing history). User docs: `docs/READABILITY.md`, `docs/RENAME.md` (the Design-D overlay the names live in).

## Files and what owns what
- `src/readability/types.ts`: every shared type and constant; `cacheKey`, `parseReadabilityResult` (never throws; strips one markdown fence), `READABILITY_MCP_TOOLS` / `READABILITY_CLI_VERBS` / `READABILITY_UI_ACTIONS` (machine-checked against spec section 9.7: rename a verb only together with the spec text), `resolveClaudeCliConfig` / `resolveHaikuConfig`.
- `src/readability/backends.ts`: the one backend-id map. `claude-cli` is the DEFAULT (Fred: run on the plan, never the API); `haiku` = API, opt-in; `replay` (committed recordings); `heuristic`; `fake`. Env `HBC2JS_LLM_BACKEND`, CLI `--backend`.
- `src/workers/backends/claude-cli.ts`: spawns `claude -p` with `--output-format json --tools "" --no-session-persistence --system-prompt <skill body>`; prompt on stdin (limit 10 MB); usage mapped to tokens; `is_error`/non-zero/timeout = `TransientBackendError`; missing binary = `ReadabilityConfigError`. The only file allowed to open a socket or spawn a model; nothing under `tests/` imports it except its stub-driven test.
- `src/readability/skills.ts` + `skills/*.md`: skill files with front matter `id`, `kind`, `version`; body sections Inputs / Rules / Output contract / Abstain. Bumping `version` re-keys the cache and REQUIRES re-keying `tests/fixtures/llm-readability/*.recording.json` with `tools/readability/rekey-recording.ts` in the same commit.
- `src/readability/cache.ts`: content-hash cache, one JSON per key under `<projectDir>/cache/llm-readability` (gitignored, derived).
- `src/readability/name-pass.ts`: `runNamePass`, the per-target loop for NAMES: targets are per-function (`{fn, regs, context}`, one model call per function, default) or per-register (`--per-register`); reply `names[]` matched by bindingId; write to the overlay as `suggested`; equiv backstop = apply-then-revert render byte-identity (whole-module `NameService.render()`, exactly twice per run, O(1)).
- `src/readability/scope.ts`: `computeSrcScope` = the segregation classifier's `src`-bucket functions (`--only src`).
- `src/readability/rewrite.ts`: `gateRewrite` / `runRewritePass`: splice a candidate function into the faithful render, run `runFunctionEquiv` (`src/harness/hbc-equiv.ts`: module-hbc leg under the Hermes VM plus a spec-09 fuzz leg when trace coverage is thin); PASS only; DIVERGENT and INCONCLUSIVE both reject; the faithful original always survives.
- `src/readability/transactions.ts` + `file-ops.ts` + `src/projdb/readability-shards.ts`: the spec-18 extension: `recordTransaction` (DB-first, then shard `analysis/readability/<id>.json`, then hash-chained log), `revertTransaction` (restores every `prior` path to its recorded sha256; revert is itself a transaction), `traceFile` (file -> origins -> `{fn,reg}`; zero-origin outputs are refused at write time). `runFileOp` for make / rename / move / combine / split with the tree-level equiv gate. Op enum includes `rewrite`.
- `src/readability/surfaces.ts`: the seven tools as plain functions over `ReadabilityContext` (`suggestNames`, `rewriteFunction`, `classifyModule`, `fileOp`, `promoteChange`, `revertChange`, `listSuggestions`). Names live in the overlay sidecar (`overlayPathFor`), addressed by `suggestionId`; rewrites/file ops in `readability_tx`, addressed by `txId`; the review tools see both. `promoteChange` refuses a `worker:` who. `loadAnalysis` is async, pool-backed, cached per (ctx, path, size, mtime). `evaluate?` is honoured via `maybeEvaluate`.
- `src/readability/evaluate.ts`: evaluator host: `evaluationModeFor` (`ui` surface ALWAYS `human-ui`; mcp/cli default `none`), plugins `NONE_PLUGIN`, `createInlineCallerPlugin`, `createAgentEvaluatorPlugin`; adversarial re-check (`skills/hbc-adversarial.md`, job kind `adversarial-recheck`) demotes `misleading` names to `low` + flagged. A report never promotes.
- `src/mcp/tools.ts`: `registerReadabilityTools` + JSON-schema validation. Spec-17's `promote` / `revert` are different tools; ours are `promote_change` / `revert_change`.
- `src/ui-server/readability-routes.ts` + `server.ts` (`buildReadabilityCtx`, `--llm-backend`): HTTP surface; the three write actions enqueue jobs (202 + jobId) and the pane polls. `src/workers/runner.ts` + `readability-worker.ts`: `readability-suggest-names` jobs run in a worker thread that opens NO project-DB connection (spec 18 single writer, DECISIONS D34); `readability-rewrite-function` / `combine-files` still run in-process (BUGS open row; needs a compute/commit split in surfaces.ts).
- `ui/src/panes/WorkersPane.tsx` (Readability section), `ui/src/workers/readability-{wire,hooks}.ts`, `ui/e2e/readability.spec.ts`. UI art direction is Fred's: extend, never restyle.
- `src/parallel/analysis-pool.ts`: `analyseModuleParallel` (stage-A pool; byte-identical by construction; default OFF below 20,000 functions, `HBC2JS_ANALYSIS_POOL=1|0`). Measured: it does not speed up setup (NSW 34 s either way). Do not reach for it to fix a slow path.
- `tools/readability/record.ts` (`--backend`, `--only src`, `--sample N --seed S`, `--resume`, `--per-register`) and `rekey-recording.ts`.
- `src/cli.ts`: verbs `name llm-fill`, `readability rewrite|file-op|review`, `hbcproj ...`, `ui-server --llm-backend`.

## Gotchas learned the hard way (each cost a relaunch once)
- `NameService.render({fn})` and the old `service.render` path emit the WHOLE module. Never call them per function or per target; use `decompileFunction` (scoped) for prompt sources. A run that did this on NSW took 38 minutes and 16 GB before its first model call.
- `decompileFunction` still re-parses and re-analyses the whole bundle per call (~1.2 s/function on the held-out app). Open BUGS row; fix = pass one parsed module/analysis through. Until then, always bound real runs with `--only src --limit N` or `--sample N`.
- Real model output arrives wrapped in ```json fences, sometimes with prose after it; `stripCodeFence` handles that. Do not assume clean JSON.
- `claude -p` refuses stdin over 10 MB; fn 0 of a bundle renders to the whole program. Skip sources over 48 KB.
- A readability job on the ui-server main thread stalls every request (ECONNRESET on `/api/modules`); that is why suggest-names runs in `readability-worker.ts`. Do not add synchronous bundle-sized work to `runReadabilityJob`.
- Playwright's role matcher is a substring match: two buttons named "Suggest name(s)" collide; use `exact: true`.
- Tailwind arbitrary px sizes fail the spec-20 token lint; use the type ramp (`text-xs` etc.).
- BUGS cells must not contain a literal `|`; Open rows need a known cluster and a `prove fixed:` verdict naming an owner or `QUEUE N`.
- Skill version bump without re-keying the synthetic recording breaks `tests/workers/backends.test.ts`.
- Spec 18 has one writer: a worker thread must not open the project DB.
- `context()`/`source()` (and so `get_context`/`get_source`, checkpoint 1a) throw "no range recorded" for every fn on a `tests/fixtures/constructs/**` fixture -- those are single-script, no `__d()` modules, so `splitProject`/`init` write zero `ix_ranges` rows (same note `tests/mcp/resources.test.ts` already carries). `suggest_names`/`promote_change` never call those two resources, so a construct fixture is still fine for exercising THEM (the mcp-server round-trip test and the agent-driver stub test both do exactly this on purpose) -- use a real bundle (`rn-template-0.72`, fn 188/190 are known-good) whenever a test needs `get_context`/`get_source` to actually return something.
- `suggest_names`' `loadAnalysis` re-parses+re-analyses the WHOLE `.hbc` file behind `ctx.hbcPath` from scratch on every call (the `decompileFunction`/`loadAnalysis` cost row above) -- one call against `rn-template-0.72` (4,199 functions) ran past a 90 s timeout with no result. `hbc2js mcp-server`'s `--hbc` and `hbc2js readability agent`'s `--hbc` do not have to name the same bytecode the project directory was `init`-ed from; a test that needs BOTH a real-bundle project (for `get_context`) AND a fast `suggest_names` call should point `--hbc` at a tiny construct fixture and accept that the two are semantically unrelated for that run.
- `hbc2js init` on `tests/fixtures/bundles/react-navigation-example-0.85.3/react-navigation-example{,.debug}.hbc` fails with `UNIQUE constraint failed: ix_ranges.fn` -- new BUGS Open row (2026-09-13, real-app cluster), not diagnosed. Blocks using this bundle (the pack's own "held-out app") for anything that needs `init`/`.hbcproj`, including the checkpoint 1b hand smoke, which ran against `rn-template-0.72`/a construct fixture instead.
- Both `suggest_names` and `heuristic`'s naming reply are PLAIN TEXT by default (`FakeBackend`'s `defaultReply`, `HeuristicBackend`'s `deriveName`), not the `{names:[...]}` JSON `parseReadabilityResult` requires -- a `suggest_names` call against either backend with no custom `replies` legitimately ABSTAINS (zero suggestions written), every time. Do not write a test that asserts a nonzero write count against `--llm-backend fake` or `heuristic`; assert the invariant that survives ("anything written is `tier:suggested`"), not the count.
- `set_name` (spec-17, `ProjectService`/DB-backed, `d_names`) and `suggest_names`/`list_suggestions` (spec-28, file-based `OverlayStore` sidecar) are TWO SEPARATE naming systems that both answer to "name" -- a `set_name` write never shows up in `list_suggestions`, and vice versa. Do not expect them to share state.
- The real `claude` binary must be directly executable (shebang + `chmod +x`) to stand in for `claudeBin` in `agent-driver.ts`/`claude-cli.ts` -- `spawn(claudeBin, args)` never goes through a shell.

## The two naming systems, and provenance filtering (open design gap)
`ReadabilityContext.who` decides who a `suggest_names`/`rewrite_function`/`file_op` write is attributed to (never the tool-call arguments -- an MCP caller cannot lie about its own identity), but nothing today lets a CALLER (the checkpoint 1b driver, in particular) pass a distinguishing run id into that `who` and then filter `list_suggestions` by it. `agent-driver.ts`'s end-of-run check works around this with a before/after snapshot diff instead of a `who`-filtered query (P-59's `NameRecord`/`ReadabilityTransaction` both carry a `who`, `ListSuggestionsFilter` does not expose one) -- correct for a single concurrent run against one project, wrong if two agent runs against the same project ever overlap. Filed here rather than as a PUSHBACK row because it was a load-tolerant implementation choice within checkpoint 1b's own scope, not a deviation from anything the spec or this pack settled.
